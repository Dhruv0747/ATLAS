# Localization CPU candidate: paced saved sensor and TF traffic

## Decision

The existing private executor adapter is a promising OFFLINE-tested candidate
for the localization monitor. Both paced windows improved in all four paired
runs. Do not install yet: these are PC measurements, not Jetson CPU savings or
proof of sufficient Astra headroom. No live hardware or service was contacted
or changed during this task. Voice, white-glass UI and safety limits remain intact.

## What changed in the test

Added `project_atlas/tools/diagnostics/benchmark_localization_traffic.py` and four
focused tests. The harness runs native ROS Humble on PC WSL, localhost-only
Domain 213, using the exact-source candidate already generated by
`benchmark_localization_executor.candidate`.

It replaces the previous burst fixture with original relative message timing,
actual saved sensor payloads and real TF buffer/listener delivery. It exercises
the captured monitor's on_scan/on_odom/on_amcl methods and captured manual
check's receive method. Both consumers subscribe to the same odometry topic.
Periodic timers remain .25/1/.25 seconds. The benchmark uses production's
blocking executor wait, not an invented polling frequency.

Odometry has two verified callback deliveries per message. Static TF is loaded
from the bag. Both latest dynamic TF edges are verified in the real TF buffer.

An additional TF audit subscriber checks decoded payloads, adding equal observer

full navigation system. No global-search worker, status-file writing, AMCL update,
reseed or manual-check request is performed. Timer callbacks are counters, not
the production schedule/publish/tick logic. This is not full localization replay.

## Results

Four interleaved original/candidate pairs per window, eight runs per window:

| Metric | Window A | Window B |
|---|---:|---:|
| Original mean process CPU seconds | 0.369529 | 0.380347 |
| Candidate mean process CPU seconds | 0.351484 | 0.345045 |
| Median paired process CPU saving | 3.8373% | 10.0336% |
| Median paired executor-thread CPU saving | 4.1814% | 10.4938% |
| Improved pairs | 4/4 | 4/4 |

Process CPU includes the synthetic publisher and verification work; the separately
measured main-thread CPU excludes publisher-thread work. Wall durations are about
6.00 and 6.18–6.23 seconds, including the final timer wake. These percentages
are NOT reductions in whole-Jetson utilization.

All 6896 expected checked callbacks delivered; no payload/order errors, duplicate
callbacks, missing messages, TF failures or shutdown failures. Worst observed
callback latency 5.167 ms; worst timer lateness 2.579 ms. Timer counts vary at
window boundaries. No hard real-time guarantee is inferred. Peak RAM was not
measured in this benchmark; no RAM improvement is claimed.

## Corrected benchmark failures (preserved, not production failures)

Initial launch incorrectly overwrote the ROS PYTHONPATH and failed to import
rclpy; harness now adds only its source directory without replacing ROS paths.
Initial CDR byte comparison rejected TF reserialization padding; the revised
check compares all decoded ROS fields against the expected message in sequence.
The first completed paced trial used a 5 ms polling timeout. Its results in
`paced-a.json` are retained but excluded: that poll introduced non-production
wakeups. A regression test now requires blocking wait. Final A/B measurements
above used blocking wait. None of these corrections changed production behavior.

`scripts/atlas_localization_monitor.py`, at its existing spin call:

## Remaining evidence and next action

The earlier Python profile still does not attribute native wait/RMW CPU or
periodic-search cost. These results establish a reproducible resource benefit
for this offline workload, not the root cause of all Jetson CPU contention.
Next useful step is the same bounded isolated workload on ARM64, only with
owner approval and unchanged production services/safety policy. No new camera
test or installation is justified solely by these PC results. No need for a
manual drive or another identical live stack capture.
