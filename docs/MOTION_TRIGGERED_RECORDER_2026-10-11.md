# Motion-triggered diagnostic recorder — offline implementation

Status: **built and tested offline; NOT deployed or enabled on ATLAS**. Autonomy and all production services are unchanged.

Update: isolated Jetson Humble serialization/SQLite validation passed; a measured preroll callback stall holds live deployment. See [Jetson validation report](MOTION_RECORDER_HUMBLE_VALIDATION_2026-10-11.md). The earlier Windows-only measurements below are historical and do not describe Jetson performance.

The opt-in `project_atlas/scripts/atlas_motion_recorder.py` uses the existing `record_atlas_demonstration.sh` topic allowlist. It subscribes only, publishes no control message, and is not attached to motor control, the mux, or the emergency stop. `--record` is mandatory. It captures a rolling ten seconds before nonzero `/cmd_vel` or measured `/yahboom/odom` movement, continues while moving, and closes ten seconds after the last movement. A second movement during that interval continues the same bag; later movement opens a new bag. `/tf_static` is pinned separately so its latched transform is available in every capture. Bag timestamps are ROS receive times; serialized source header timestamps are preserved in the messages.

Captured topics include raw M1–M4 encoder values, `/yahboom/odom`, IM10A bias-corrected candidate, `/imu/data`, `/odom`, `/scan`, `/scan_raw`, `/amcl_pose`, `/tf`, `/tf_static`, all existing recorded command sources, steering commands, encoder health, and control policy. A missing or stale topic appears in `recorder_health.json`; it does not fabricate data or interrupt control. The manifest records per-topic received and written counts and application-level drops. DDS/RMW losses cannot be reconstructed exactly from this subscription alone and are explicitly marked `unmeasured`, not zero.

Each bag has a unique `capture_*` directory. The process counts only its own capture directories toward a 500 MiB total quota, reserves 20 MiB for bag/manifest overhead, and refuses new captures when insufficient quota or less than 1 GiB of disk is free. It closes and disables recording when a write fails or the storage cap is reached. **It never prunes or overwrites any recording**, including an incomplete capture left by a crash or older diagnostic evidence outside its root. The in-memory preroll is capped at 64 MiB and evictions are counted. A process restart can start a fresh capture but cannot recover preroll from before the crash.

Offline validation: `python -m unittest project_atlas.tests.test_atlas_motion_recorder -v`. Cases cover idle startup, preroll/postroll and original timestamps, repeated short movement, missing/stale sensors, write/open failures, storage cap, and preservation of existing evidence. Synthetic benchmark: `python project_atlas/tools/diagnostics/bench_motion_recorder.py`. These do not run ROS or move ATLAS. Jetson serialization and resource measurements are now completed in the linked validation report; callback blocking and subsequent live-subscription validation remain deployment gates. The Windows benchmark measures only the Python state machine/file-writing workload.

2026-10-11 offline Windows benchmark: 60 seconds of synthetic traffic processed in 0.114 s wall / 0.109 s CPU, with 1.76 MiB peak traced Python allocations and 7,027,200 bytes written (6.7 MiB per simulated minute). The displayed near-100% CPU is **accelerated benchmark execution**, not projected live CPU. At a paced 60-second rate, the measured core-work CPU time would be about 0.18% of one core; ROS subscriptions and sqlite3 bag-writing overhead are not included, so this is not a Jetson deployment estimate. No message drops occurred in the synthetic run.

Installation plan, **only after operator approval**: copy these two scripts to the Jetson alongside existing scripts; run a short isolated bag-writer smoke test without subscriptions; verify available disk; start the recorder manually with `--record` while motors remain off; verify message-age and topic counts; then assess overhead during a supervised drive. Do not create an autostart service or alter Nav2/motor units during this phase. Rollback: stop the recorder process (Ctrl-C), which closes its active bag; leave capture files intact; remove or disable only this opt-in recorder command. No production service or parameter rollback is necessary because none was changed.
