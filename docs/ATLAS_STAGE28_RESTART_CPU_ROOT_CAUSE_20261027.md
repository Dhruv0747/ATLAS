# Stage 28 — root cause of the service-restart CPU spike, and options (offline), 2026-10-27

Scope: analysis and offline tests only. No deployment, no restart, no production change. Jetson access was read-only:
`journalctl`, `systemctl show`, `/proc`, `/sys/fs/cgroup`, and existing evidence files.

## 1. Root cause

The spike is **not** mainly the restarted process. It is ROS 2 graph discovery work done by **every other participant**
when a new participant appears. There are **44 other DDS participants** on the Jetson (counted from `/proc/*/maps`).

| Restart | Baseline % | Restarted process (core-s) | All other processes (core-s) | Peer share | 1-s samples > 75 % | Last > 75 % |
|---|---|---|---|---|---|---|
| atlas-sensor-recovery, Stage A, 2026-10-27 | 64.4 | 1.4 (systemd accounting: 7.0 s in 30.5 s vs 0.183 core steady) | 11.9 | **89 %** | 7 | +8.5 s |
| rover-status-web, 2026-10-21 (per-process trace) | 65.6 | 0.8 | 36.8 | **98 %** | 19 | +25.4 s |
| rover-status-web, 2026-10-24 (per-process trace) | 72.9 | 0.4 | 37.7 | **99 %** | 24 | +27.1 s |

**Per-process traces.** In both web restarts the plateau (93–100 % for ~20 s) is spread across nodes that have nothing
new to do. Each of these gains +8–16 % of a core:
- both `static_transform_publisher`s;
- `ekf_node` ×2, `lifecycle_manager` ×2;
- `planner_server`, `bt_navigator`, `amcl`, `foxglove_bridge`;
- the Python ATLAS nodes.

The restarted web process itself appears only briefly (+33/+47 % of a core at +5–6 s). This is the signature of
DDS endpoint discovery plus the per-node ROS graph-cache updates that every participant performs.

**Recovery timing (journal, short-precise).**

| Time | Event |
|---|---|
| 20:57:36.31 | Started |
| 20:57:39.24 | "coordination: loaded" (2.9 s: `bash -l`, `setup.bash`, imports, `rclpy.init`, Node) |
| 20:57:39.47 | READY (subscriptions and publishers created in 0.23 s) |
| ≈38.3–44.3 | CPU recorder shows the spike, which continues ~5 s after READY while recovery idles in its 30 s grace |

**Phase contribution (recovery restart).**

| Phase | Machine CPU added | Core-seconds |
|---|---|---|
| Interpreter start, `setup.bash`, imports, `rclpy.init`, node creation | +6.6–7.1 points for ~2 s | ≈1.2–1.4 (own process) |
| Endpoint creation (18 own + 14 default per node) | 0.23 s in-process | negligible |
| Timers (2) | — | negligible at start; steady recovery = 0.18 core |
| Discovery / graph processing in the 44 peers | spike to 95.3–99.8 % | **≈11.9 (89 %)** |

A finer in-process split of imports vs. `rclpy.init` needs a per-process trace of a real restart. That was not
collected and must not be generated by restarting a service now.

**No degradation logged during the spike.** 20:57:38–46: 0 warnings or errors other than the rf2o "Waiting for
laser_scans" background, which runs at the same rate before and after. No safety snapshot was *sampled* during the
spike, so telemetry freshness during a transient remains unproven. The transient rule below therefore samples safety
throughout its window.

### Side finding: CPU resource control is not in effect for user services

The user manager delegates only `memory pids`, not `cpu`:
`/sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/cgroup.subtree_control`.

- `rover-base-telemetry`'s `CPUWeight=1000` (unit plus `priority.conf`) **has never been applied**: there is no
  `cpu.weight` in its cgroup.
- Any `CPUQuota=` on a user unit would be silently ignored.

This is a separate issue from Stage 28 and is not changed here.

## 2. Cost model (offline, from the three measured restarts)

Linear fit, whole-Jetson excess core-seconds = **5.52 per new participant** (paid mostly by peers, independent of
endpoints) + **0.243 per endpoint**.

Endpoint counts from source:

| Node | Endpoints |
|---|---|
| recovery | 32 (18 + 14 default: 6 parameter services ×2, `/parameter_events`, `/rosout`) |
| web | ≈133 |
| base | ≈80 |

Queue model: the work drains at 0.85 × idle CPU per second. Monte Carlo over the 120 real 1-s baseline samples
(mean 65.35 %, p95 67.34 %, max 68.87 %) reproduces the measurements:
- R0 recovery: 7 samples over 75 %, last at +9 s (measured: 7 samples, last +8.5 s);
- W0 web: 22 samples over, last at +27 s (measured: 19/24 samples, last +25.4/+27.1 s).

Caveat: two node types and three events; the fixed/per-endpoint split is approximate.

### Evidence-supported bounds (not 120 s)

**Recovery: 10 s.** The measured last over-limit sample was at +8.5 s and the first clean sample at +9.5 s; 10 s is the
shortest whole-second bound that contains that observation. The model, across the real baseline distribution, gives
p95 9 s and max 10 s. The two web restarts differ by only 1.7 s at baselines 7 points apart, which suggests end
times are reproducible. 8 s fails the measured series (test).

**Base, Stage B: not yet supportable from measurement.** Two candidates:
- Model: last over-limit at 17 s (p50) / 18 s (p95, max).
- Measured envelope on this rover, from a larger node (web, ~133 endpoints): 27.1 s.

Recommendation: decide after Stage A adds a second recovery measurement. Use the model value (18 s) only if the owner
accepts that a miss means a base rollback restart.

## 5. Offline tests

- **42 unit tests** (`project_atlas/tests/test_base_maintenance.py`) pass on Python 3.10 and 3.13. New tests for the transient rule:
  - the measured Stage A series passes 10 s and fails 8 s and strict;
  - any sample > 75 % after the bound fails;
  - RAM/temperature violations and unreadable samples fail even inside the window;
  - a safety failure inside the window fails;
  - the bound is mandatory and capped at 30 s, and strict takes none;
  - strict still judges every sample from the restart.
- **Real systemd 255 simulation, Python 3.10:** s01 (stage A, transient 10 s), s02 (strict rolls back), s03, s04b, s05, s06 (spike beyond the bound → FAIL, late samples listed) and s07 all PASS.
- **Analysis tool** `project_atlas/tools/diagnostics/stage28_restart_cpu/analyze_restart_cpu.py` (raw traces stay on the Jetson).

## 6. Recommendation: smallest safe change

**Option C, deployer-only**, for Stage A with `--cpu-rule transient --transient-bound-s 10`:
- No production code, unit or limit changes.
- The Stage A files and their hashes (MANIFEST) are unchanged.
- Rollback restarts are now also recorded and reported.

This is an explicit, narrow exception to "every 1-s sample ≤ 75 %". It applies only inside the first 10 s of one
approved restart, with all samples reported. It needs the owner's decision.

Option A-R1 can be added later to shorten the window by ~1 s, but it is not needed. Option B is rejected on evidence.
Stage B's bound is to be set after Stage A.
