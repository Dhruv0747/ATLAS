Date 2026-10-21. Owner approval (14:50 IST) covers development and testing of option (a) only. **Nothing was installed on the Jetson, no service was restarted, and there was no camera start.** Installing the guard and any further live Depth test each need separate approval.

## 1. Stale-summary UI bug: fixed

**Symptom (test 2, 14:44).** For about 4 s after Start, the page showed the previous session ("Camera off … Stopped safely").

**Fix (`web/v2/vision3d.js`).** On Start the page records the previous `worker_pid` and immediately shows "Checking before start". Any runtime state carrying the old `worker_pid`, including replies that were already in flight, is shown as "checking" until the new worker reports. There is a 20 s safety timeout, and a new worker that dies early is still shown.

**Test.** `tests/test_vision3d_stage31b_ui.py` runs headless Chromium against a scripted server that keeps returning the old session for 3 s after Start.
- It **fails on the deployed `vision3d.js`**, reproducing the bug.
- It **passes with the fix**: the page shows only "Checking before start" until the new session's state arrives, the old driver state is never shown, and exactly one Start POST is sent.

## 2. Guard candidate: minimum 1-second CPU window

**Changed file:** `scripts/atlas_vision3d_runtime.py`, viewer worker only.

| | Deployed (Stage 31) | Candidate |
|---|---|---|
| CPU sample window after launch | ~0.5–1.5 s, often 0.5 s (lease arrivals end the `select` early, then a 0.5 s sleep) | **1.0 s minimum**: a sample is never taken before 1.0 s has elapsed |
| Decision | one sample > 75% → stop | **unchanged**: one sample > 75% → stop |
| RAM 80% / temperature 70 °C / policy and freshness / service identity / child alive | every sample | **unchanged**, every sample (≈1 Hz) |
| Longest allowed window | not enforced | **2.0 s**: a longer window (stalled guardian, slow safety snapshot) **fails closed** as RESOURCE BLOCKED |
| Lease (pause, close, hide) check | every ≤ 1.5 s | every ≤ 0.25 s; 4 s expiry unchanged |
| Start-up grace / limit change / service pausing | none | **none** |

- `tools/vision3d/stationary_gate.py` (the 75/80/70 checks) is unchanged and byte-identical to the deployed file, which a test asserts.
- No other production file changes.
- The worker re-reads the runtime file at each explicit Start, so installing it needs **no service restart**.

Generated by `tools/vision3d/stage31b_replay.py` → `evidence/stage31_live_b/replay_old_vs_candidate.json`. Limit 75% for both.

| Trace (1-second whole-machine samples) | Max | Deployed guard | Candidate (1 s windows) |
|---|---|---|---|
| Test 2 at 14:44 (191 s, persistent recorder) | 73.75% | **BLOCKED** on a 0.68 s window at 76.0% | **PASS**: no 1-s sample above 75% |
| Parked baseline, no join | 66.6% | pass | pass |
| ROS join in production domain 0 | 92.1% (3 s) | block | **BLOCK** (75.1, 92.0, 92.1) |
| ROS CLI start in private domain 77 | 76.6% (1 s) | block | **BLOCK** (76.6): a full one-second burst still trips it |
| Test 1 at 14:32 | 77.8% final sample | blocked | **cannot be replayed**: no per-second trace survived and the window length is unknown |

**What the longer window forgives:** a full-machine burst no longer than 0.29 s on a 65% baseline (0.17 s at 69.8%). The deployed 0.5 s window forgives at most 0.14 s.

**Limits of this evidence:** the replay uses 1-s bins aligned to the recorder, not the guard's own windows. A live start could still meet a window above 75%, for example if the Astra start-up burst and a network probe fall inside the same full second. **A live pass is likely, not guaranteed.** The guard is reactive: it decides whether to keep streaming and does not protect sub-second control timing. That timing stays with the independent E-STOP and mux services.
